# 第 4 课 · 让 agent 好用

> 目标：REPL、中止、会话持久化、上下文预算、错误重试——把玩具变成每天能用的工具。
> 实现规格：[specs/04-usable.md](../specs/04-usable.md) · Tag `l4-usable` · 约 100 分钟

## 这节课要回答的问题

**为什么 demo 里很漂亮的 agent，一到真实任务就崩？**

因为真实任务意味着：聊几十轮（上下文会满）、跑很久（你会想中断）、中途出错（网络会抖）、明天还要接着干（状态要留下）。这四件事没有一件和「智能」有关，但少任何一件，第 5 课的实战都会死在半路。

这节课不性感，但它是 L5 能否交付的分水岭。

第 3 课的 agent 能改文件。

## 课堂流程

### 1. REPL（15 分钟）

`node:readline/promises` 起一个循环，加几个斜杠命令：`/exit`、`/clear`（清空历史保留 system）、`/history`（消息条数与估算 token）、`/save <name>`。

流式输出做一点区分：正文正常打印，思考过程用暗色 `\x1b[2m` 包起来，工具调用打印一行 `· read(path=src/a.ts)` 并在结束后带上耗时。

**不要做 TUI。** 差分渲染、光标控制、滚动区域——那是另一门课，而且会掩盖 agent 的事件流。我们要让学员始终看得见「发生了什么」。

### 2. 故障注入 —— 中止（25 分钟）

让 agent 执行一个长任务，按 Ctrl+C。

第一次实现几乎必然是坏的：**按下去了，但它还在打字。** 或者更糟，进程退出了，但 `bash` 起的子进程还在后台跑。

让学员自己找原因。答案是 `AbortSignal` 必须贯穿三层，缺一层就漏：

```
SIGINT → controller.abort()
      → fetch 的 signal          （不传：SSE 继续流，字还在蹦）
      → 工具 ctx.signal          （不传：bash 子进程继续跑）
      → loop 检查 signal.aborted （不查：当前工具停了，下一步照常开始）
```

三层都接上之后还有一个隐蔽问题：**中止时已经产生的部分消息怎么办？**

如果模型已经发出了 `tool_calls` 但工具还没执行完就被中止，此时若把 assistant 消息丢掉、只留 user 消息，下一轮就会出现「有 tool 结果但没有对应 assistant」或反之的孤儿状态，服务端 400。

正确做法：保留已产生的消息，给未完成的工具补一条 `[aborted]` 的 tool 结果。**对话状态的完整性比干净更重要。**

这一节很值得慢慢讲，它是学员第一次真正体会到「agent 是有状态的系统」。

### 3. 会话持久化（15 分钟）

一行一条消息的 JSONL，消息产生时立刻 append：

```ts
appendFile(file, JSON.stringify(msg) + "\n")
```

为什么是 append-only 而不是「退出时把数组写进去」：**崩溃、断电、Ctrl+C 都不该丢历史**，append 最多丢最后一行。读取时跳过解析失败的行（崩溃可能留下半行）。

代价也要讲清楚：没有分支、没有压缩、没有索引。第 5 课会亲身体会这些代价。

### 4. 故障注入 —— 上下文炸掉（25 分钟）

**本课最重要的一节。**

构造一个长会话（或者让 agent 连读几个大文件），继续聊，直到服务端返回：

```
400: the request exceeds the available context size
```

整个会话作废。这就是第 5 课最常见的死法。

先让学员理解「上下文是怎么花光的」：`/history` 命令实时显示估算用量。会发现**工具结果是大头**——一次 `read` 可能就是几千 token，几次下来就见底了。

然后写 `fitContext()`。策略不复杂：保留 system、保留最近 4 轮、从最老的开始丢，直到低于预算（上下文的 70%）。

但有一个必须讲的陷阱：**丢弃必须成组。**

一条 `assistant(tool_calls)` 和它对应的所有 `role: "tool"` 消息，要么都留要么都丢。只丢一半会产生孤儿 `tool_call_id`，服务端 400——你为了避免 400 做的裁剪，制造了另一个 400。这个 bug 非常常见，值得当场演示一次。

token 估算不引 tokenizer（零依赖原则），但系数要实测。课堂上当场量一次：用 `max_tokens: 1` 发请求，读响应里的 `usage.prompt_tokens`，减去对话模板开销。

本机对 Qwen3.8 的实测结果：**中文散文 0.58 token/字，TypeScript 代码 3.7 字符/token。** 于是估算函数是 `cjk * 0.7 + (其余字符) / 3.5`，各留约 20% 余量。

顺便展示两个错误取值，让学员理解为什么要实测：

- `chars / 3` 一刀切：对中文低估约 1.8 倍。这门课全程中文交互，低估意味着以为还有余量、实际已经贴着 65536——**为了避免 400 写的裁剪，反而保证了会 400。**
- CJK 一律按 1 token/字：比实测高 1.7 倍。安全但浪费，真实用量才 60% 就开始裁剪，第 5 课那种长任务经不起这么糟蹋。

十分钟的实测，胜过任何一篇博客上抄来的经验值。

### 5. 重试（10 分钟）

网络会抖，服务会 503，llama.cpp 单并发时第二个请求会排队甚至超时。

规则要讲清楚**什么不该重试**：

- 重试：网络错误、5xx、429（尊重 `Retry-After`）
- 不重试：4xx（除 429）——请求本身就是错的，重试只是重复失败
- 不重试：已经收到第一个 token 的流——重来会产生重复内容，只能上报错误

指数退避 + 抖动，每次重试打印一行提示。**不要静默重试**，学员要看得见发生了什么，否则一个「有点慢」的会话背后可能藏着 5 次失败。

### 6. 见真章（10 分钟）

```bash
node src/cli.ts --cwd demo/tmp -s work.jsonl
```

连续聊十几轮，读几个大文件，中途 Ctrl+C 一次，退出后 `-c` 续聊。它应该：不炸上下文、能干净中止、记得上文。

**现在它是一个你愿意每天打开的工具了。** 1200 行。

### 7. pi 对照（10 分钟）

pi 在这些地方比我们多做的：

| 能力 | 我们 | pi |
|---|---|---|
| 上下文管理 | 丢最老的轮次 | **compaction**：用 LLM 把旧对话总结成摘要再保留 |
| 会话 | 一行一条的 JSONL | 带 header、分支（fork）、lane、崩溃恢复的状态机 |
| 中止 | 一个 AbortController | 区分 abort / suspend / deferred，可恢复 |

打开 `pi/packages/agent/docs/harness.md` 看一眼那个 durable runtime 的设计：操作状态机、conversation tree、usage ledger。

**要讲清楚的判断是**：这些机制解决的是「长时间、多分支、可恢复」的真实产品需求，代价是巨大的复杂度。教学 agent 不需要，但你要知道它们为什么存在——当你的 agent 开始被别人依赖时，你会一个一个把它们补回来。

丢弃历史 vs 总结历史，这个取舍尤其值得讨论：我们丢掉的信息模型再也看不到了；pi 的 compaction 保留了摘要，但要多花一次 LLM 调用，而且摘要本身可能丢关键细节。**没有免费的午餐。**

## 练习

1. 实现 compaction：上下文超阈值时，用一次 LLM 调用把最老的若干轮总结成一段摘要。对比它和「直接丢弃」的效果差异。
2. 给 `/history` 加上分类统计（system / 用户消息 / 工具结果各占多少），找出上下文都被谁吃掉了。
3. 实现会话分支：从历史中某条消息开始一条新对话。
4. 给 REPL 加输入历史（上下方向键）。
5. 思考题：如果两个 agent 实例同时写同一个会话文件会怎样？最小的修复是什么？

## 本课完成标准

- REPL 连聊 5 轮以上稳定，Ctrl+C 只停当前轮且子进程被杀
- 退出后 `-c` 续聊，模型记得上文
- 人为构造超长会话，自动裁剪而不是 400
- 累计 ≤ 1200 行，`node --test` 全绿且离线可跑
