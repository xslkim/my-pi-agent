>>> 环境基线：三条 #B03
先说环境基线，只有三条。
第一，**Node 二十三点六**及以上，原生运行 TypeScript。
二十二点几的版本，要加一个类型剥离标志。
第二，运行时依赖为零。
第三，模型接入只有三个环境变量，代码里不设默认值。
三条都满足，就可以开始写代码了。


>>> 现象：curl 打端点看原始字节流 #B04
写代码之前，先看看协议本身长什么样。
用 curl 直接打模型端点，要求流式返回。
不用任何库，curl 就是最小的客户端。
屏幕上滚动的，就是原始的 **SSE** 字节流。
这一集要写的客户端，就是读懂这堆字节。


>>> 读流：事件结构与两个关键字段 #B05
凑近看这块字节流的结构。
每个事件是 data 冒号加一段 JSON，用空行结尾。
正文增量藏在 choices 第一项的 **delta.content** 里。
模型说完了，会发来一个特殊的 **[DONE]** 事件。
收到 DONE，客户端就知道流结束了。
结构看清了，难点在下一节。


>>> llama.cpp 特有：reasoning_content #B06
还有一个字段，是 llama.cpp 特有的。
思考增量不在 content 里，在 **reasoning_content** 里。
我们的默认模型 qwen3.8-27b，就会输出思考。
客户端要同时接住两股流：思考和正文。
把思考也逐字显示出来，是本集的目标之一。


>>> 核心难点：TCP 不保证事件边界 #B07
现在到了本集的核心难点。
**TCP 不保证事件边界**。
一个完整的事件，可能被切成两半，分两次到达。
也可能一个半事件，挤在同一块里到达。
网络只给你字节流，事件边界要自己找。
你把流当成消息来读，就已经错了。


>>> 故障注入：天真的 split #B08
不信的话，做个故障注入。
天真的写法，是按两个换行直接 **split**。
事件被切半的时候，JSON 解析直接报错。
更糟的是丢字：半段事件被当成完整事件。
终端里看到的，就是乱码和缺字。
这不是模型的问题，是解析器太天真。


>>> 修法：跨 chunk 缓冲区 #B09
修法，是一个跨 chunk 的 **缓冲区**。
每来一块字节，先拼到缓冲区尾部。
只切出完整的事件，切剩的尾巴留在缓冲区。
下一块到了再拼，拼完再切。
这样不管 TCP 怎么切，事件一个都不丢。
这就是手写解析器的核心。


>>> 代码走读：llm.ts 主循环 #B10
这套逻辑落在 llm.ts 里，l1-talk 时只有 **七十八行**。
发起请求，拿到响应的字节流。
缓冲区切出完整事件，尾巴留下。
正文和思考分别取出，逐字打印到终端。
收到 DONE 就关掉流，一轮对话完成。
走读一遍主循环，你也能手写一个。
