>>> 为什么不 import pi #B03
参照工业级实现 **pi**，但一行不 import
它的模型兼容层 **一千五百七十七行**，我们一百四十九行
差额不是水分，是四十家厂商的 **兼容性税**
单端点场景不用交这个税
但要知道税单上写了什么，否则你永远读不懂它的源码

>>> 先抓包，再写代码 #B05
第一集不急着写代码，先 curl 看真实字节流
**SSE**：事件以 data 冒号开头
**两个换行** 分隔，data 中括号 DONE 收尾
规格文档写得再好，字节流才是唯一的事实来源

>>> 一个事件的解剖 #B06
content 是正文 **增量**，不是完整回答
reasoning_content 是思考增量，llama.cpp 特有的字段
finish_reason 标记停止原因
所谓流式，就是把一次响应拆成碎片逐个下发

>>> 天真解析器 #B07
直觉写法：收到一块切一块
错在假设 **TCP 保住事件边界**——它不保
一个事件可能被切成两半到达
天真解析器拿到半截 JSON，直接炸
这是流式客户端的第一类经典错误

>>> 修复一 · 跨 chunk 缓冲 #B08
修法是标准做法：维护一个 **缓冲区**
每块先进 buffer，循环找双换行
凑齐完整事件才处理
半截的留在 buffer，等下一块到齐
两行代码，但必须先看见它坏掉再修

>>> 修复二 · 多字节切分 #B09
藏得更深的坑在 **UTF-8** 多字节字符
一个汉字三个字节，可能正好被切在中间
半截字节直接 decode，输出就是乱码
修法一行：decode 加 **stream true**
让解码器自己留存不完整的字节

>>> 修复三 · 延迟的 done #B10
这个坑只有真机抓包才看得到
finish_reason 和 usage **不在同一块**
带 usage 的末块，choices 是空数组
看到 finish_reason 就发 done，token 统计永远是空
正确做法：两个都缓存，**流结束再统一发 done**
第四集的用量统计，全压在这个设计上

>>> 故障注入基建 #B11
这三个坑不能靠真机偶发去碰运气
写一个 **假模型服务器**，按脚本回放字节流
可以切在任意字节边界，包括汉字中间
测试毫秒级、离线、可复现
能伪造协议，才算真的懂协议

>>> streamChat 的接口形状 #B12
客户端做成 **async generator**
for await 消费，天然支持提前 break，背压不用自己管
这个接口选择，让第四集的中止功能便宜了一半
回调方案到那时候会开始还债
测试也简单：收集成数组就能断言

>>> pi 对照 #B13
pi 的兼容层一千五百七十七行
光思考字段就认三个名字，还得防厂商重复返回
我们只服务一个端点，这个标签下 **七十八行**
结课也只涨到一百四十九行
多出来的一千四百行，每行都对应一家厂商的怪癖

>>> 小结 #B14
第一集的三个坑，全部来自真实字节流
