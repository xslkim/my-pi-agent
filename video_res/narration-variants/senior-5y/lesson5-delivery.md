>>> 交付，不是演示 #B01
最后一集不讲新概念，做 **交付**
任务是真的，验收是自动化的，失败是公开的
课程设计里，预期它第一次会失败
因为 **失败清单才是本集的主要产出**

>>> 任务与约束 #B02
空目录里做一个登录应用
后端四个接口，sqlite 存用户
密码 scrypt 加盐哈希，**禁止明文**
会话用 httpOnly cookie，前端原生 JS
约束三条：零依赖、两轮 prompt 逐字相同、全程不干预

>>> 验收先行 #B03
核心设计：**验收先行**
十条冒烟断言，agent 进场之前写好并锁定
最狠的一条：直接搜数据库文件的原始字节
明文密码一个字节都不许出现
验收先行，通过就是通过
没有「我觉得差不多」这个状态

>>> 两道锁 #B04
考卷不许改，上两道锁
第一道：路径约束，agent 的文件工具够不到验收目录
但 bash 能用绝对路径绕过——第三集练习里就点破的缺口
不遮掩，诚实承认
第二道：**校验和兜底**，考卷动一个字节，验收作废
每轮验收前，人先跑一次 verify-lock
**声明式约束挡不住能执行任意命令的工具**
这正是 pi 要做沙箱和权限确认的原因

>>> 裸跑 run1 #B05
裸跑，全程录屏，不干预
Windows 加 Git Bash，模型在局域网
结果先剧透：十条验收，一次就 **全绿**
预判的七个缺口，六个没有发生
但它真的死了一次

>>> 死锁解剖 #B06
它起后台服务自测，然后 bash 工具 **永久挂死**
根因：工具等的不是进程退出，是 **全部 stdio 关闭**
超时杀掉了 bash
但后台服务进程还活着，手里握着管道
close 事件永远不来
人工杀掉占端口的进程才恢复

>>> 失败记录表 #B07
事故进 **失败记录表**：现象、根因、对策，一一对应
预判清单里七项缺口，没发生的 **一个都不做**
包括 ls 和 grep 工具——没有证据，直接砍掉
加固由 **证据驱动**，不由想象驱动
给想象中的 agent 加固
和凭直觉优化性能一样不可靠

>>> 三层修复 #B08
一个事故，挖出三层
第一层：以进程 exit 为准返回，宽限一秒后主动 destroy 流
第二层：又发现外部杀不到后台任务
Git Bash 的后台进程，根本不在 Windows 进程树里
第三层：让 bash 自己清场，退出前 kill 掉所有 jobs
一三层通用，第二层 Windows 专属
每一步修复，都有实验证据

>>> run2 验收 #B09
修完跑 run2：同一命令、同一 prompt、空目录重来
这一次自测没有挂死
**七步、九次工具调用**——上次是十一步、十七次
先验考卷，校验和一致
再跑冒烟，十条断言 **全绿**
零人工救援

>>> run1 对 run2 #B10
有意思的对比：登录应用两次都做出来了
差别不在产出，在 **过程**
run1 要人工救一次，run2 一次都不用
把人从救援里解放出来，才是加固的意义
这也是「能跑」和「能用」之间的全部距离

>>> 复盘 #B11
它为什么能成：边界清晰、验收可执行、工具够用
为什么差点没成：每个简化决定，都会被真实任务逼出来
pi 怎么解决：compaction、沙箱、并行工具、可恢复中止
每一个都对应我们简化掉、或差点踩中的决定
当初看着像过度设计的东西
现在都对应一个亲手踩过的坑

>>> 收束 #B12
这门课的终点
不是造一个替代 pi 的 agent
是获得 **读懂它、并判断自己需不需要它** 的能力
架构、取舍、坑，你都亲手过了一遍
剩下的，是你自己的工程判断
