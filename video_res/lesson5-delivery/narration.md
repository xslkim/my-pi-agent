>>> 第 5 课开场 #B01
最后一课不是讲课，是 **交付**
前四课造的这个东西，到底能不能干活
任务是真的，验收是自动化的
失败是公开的
这一课有个反直觉的设计
我们预期它第一次 **会失败**


>>> 任务定义 #B02
任务：在一个空目录里，做一个登录应用
后端四个接口，sqlite 存用户
密码 scrypt 加盐哈希，**禁止明文**
会话用 httpOnly cookie
前端原生 JS
约束就三条：零依赖，两轮逐字相同的 prompt，全程不干预


>>> 验收先行 #B03
关键设计，**验收先行**
冒烟测试十条，在 agent 进场之前写好并锁定
从注册到登出，覆盖全部接口
最后一条最狠
直接搜数据库文件的原始字节
明文密码一个字节都不许出现
验收先行，通过就是通过


>>> 两道锁 #B04
agent 不许改考卷，上两道锁
第一道，路径约束让它够不到验收目录
但 bash 能用绝对路径绕过，我们诚实承认
第二道，校验和兜底
考卷改动一个字节，验收作废
它是人手动跑的：每轮验收前，人先跑一次 verify-lock
**声明式约束挡不住能执行任意命令的工具**
这正是 pi 要做沙箱和权限确认的原因


>>> 裸跑开始 #B05
裸跑开始，全程录屏，不干预
跑在 Windows + Git Bash 上，模型在局域网
考卷和 prompt 都在仓库里，照着跑就行
任务描述来自锁定的 prompt 文件
两轮运行逐字一致，由校验和保证
课程的设计里，它预期会失败
因为 **失败清单才是这一课的主要产出**


>>> run1 实况 #B06
真实的 run1 是这样的
它写完了全部五个文件，做得很顺
然后想后台起个服务自测
接着，**卡死了**
注意，这不是剧本
是这门课真实发生的事故


>>> 死锁解剖 #B07
解剖这次死锁
工具等的不是「进程退出」
而是「**全部 stdio 关闭**」
bash 被超时杀掉了
但后台的服务进程还活着，手里握着管道
close 事件永远不来
必须人工杀掉那个进程才恢复


>>> 失败记录表 #B08
事故记进 **失败记录表**
现象、根因、对策，一一对应
预判清单里列了七项缺口
但 run1 里没发生的，一个都不做
加固由 **证据驱动**
不由想象驱动
这份表，是整个第五课最重要的产出


>>> 回炉 · 三层修复 #B09
回炉修复，一个事故挖出三层
还记得吗，我们跑在 Git Bash 上
第一层，改成以进程 exit 为准返回
宽限一秒后主动 destroy 流，不再傻等 close
第二层，又发现外部杀不到后台任务
Git Bash 的后台任务，根本不在 Windows 进程树里
第三层，让 bash 自己清场
退出前 kill 掉所有后台任务
第一层和第三层是通用的，第二层是 Windows 专属
修复的每一步，都有实验证据


>>> run2 与验收 #B10
修完之后，run2
同一个命令，同一个 prompt，从空目录重跑
这一次自测没有卡死
而且只用了 **7 步**、9 次工具调用
上次是 11 步、17 次
先验考卷，校验和一致
再跑冒烟测试
十条断言，**全绿**


>>> run1 vs run2 #B11
run1 和 run2 的对比，就是整门课的结论
有意思的是，登录应用两次都做出来了
差别在别的地方
run1 需要人工救一次
run2 一次都不需要
**把人从救援里解放出来**
这才是加固的意义


>>> 复盘收束 #B12
最后复盘三个问题
它为什么能成？边界清晰，验收可执行，工具够用
它为什么差点没成？
每个简化决定，都可能被真实任务逼出来
pi 是怎么解决的？
摘要压缩、沙箱、并行工具、可恢复中止
每个都对应这门课里，我们简化掉、或差点踩中的决定
这门课的终点
不是造一个替代 pi 的 agent
而是获得 **读懂它、并判断自己需不需要它** 的能力
